# Proccoli: Build Plan

An incremental plan. Each milestone:

- adds **one** capability on top of a working app,
- lists **what to create, in order**, with the test that proves each piece
  works before moving on,
- ends with a **definition of done** that a user can check by running
  `make run` (or `make demo` once fixtures exist).

Class and module names refer to [DESIGN.md](DESIGN.md). Section references
(§) point there.

**Working rules for every milestone**

1. Write the test with (or before) the class. Domain and core code must be
   testable without a display.
2. Every `/proc` and `/sys` read goes through `SysRoot`, so its test uses a
   fixture tree under `tests/fixtures/`. Capture fixtures from real machines
   with `tests/fixtures/capture.sh` (Milestone 2).
3. UI code gets a **smoke test**: build the widget and feed it a snapshot, on
   the headless Broadway backend (`GDK_BACKEND=broadway`, `make ui-test`).
   Visual checks use the screenshot script from Milestone 1.
4. `make test` stays green at the end of every step, not only at the end of
   each milestone.
5. Commit at the end of every numbered step.

**Deviations from the original plan, and why:**

- **2.6:** there's no need for `make run` to set `GSETTINGS_SCHEMA_DIR`.
  `Settings.load()` compiles the source checkout's schema into
  `build/schemas/` by itself, so `python3 -m proccoli` works without make.
- **2.8, 3.7:** these depend on Milestone 1's pages and sidebar, which were
  skipped for now. The parts that don't are done. The rest moved to steps
  1.8 and 1.9.
- **1.7:** `tests/run-headless.sh` (a private Broadway display with in-memory
  settings and no D-Bus) was built early, for the M3 widget tests. The
  screenshot harness uses 1024×768 instead of 1280×800, because that's the
  largest screen Broadway offers.
- **1.4:** the primary menu's Preferences, Keyboard Shortcuts and About
  entries are present but greyed out until Milestones 13 and 15 add their
  actions.
- **1.6:** Adwaita has no CPU or memory icons, and Resources' icons are GPL.
  Processor uses `computer-symbolic` and Memory uses `media-flash-symbolic`
  until our own icons arrive in Milestone 15.
- **Added:** a page lifecycle (`ResourcePage.track()` / `shutdown()`, see
  DESIGN §9), so swapped or removed pages disconnect cleanly.
- **4–9, added:** a shared `DevicePage` base (`ui/pages/device.py`) for
  every device page: graph and unit preferences, redraw only while visible,
  sidebar summary, Properties group and an optional banner. `DeviceManager`
  and the demo device move the demo out of the window.
- **6:** the sidebar title of a drive is its type ("Solid State Drive",
  "NVMe Drive", ...), with the model as the description. The generic SCSI
  vendor "ATA" is dropped from model names.
- **7:** manufacturer names come from the system's `pci.ids` (`core/pciids.py`,
  also used for GPU names). Network interfaces have no percentage, so the
  sidebar shows no progress bar for them; the graph meter auto-scales to the
  receive rate (`SidebarSummary.max_value`).
- **8:** on this laptop `perf_event_paranoid` is 4, so intel_gpu_top needs
  administrator rights. As designed, the GPU page doesn't ask for a password
  at start-up: its Details and Processes tabs offer "Show Detailed
  Statistics" instead (originally a banner on a swapped-in summary page,
  see the GPU tabs refactor). The generic backend can only count the user's own
  processes on Intel iGPUs (no `gpu_busy_percent`), and says so on the page.
- **9:** `--demo` adds a synthetic Intel GPU with both data sources (the
  summary one also synthetic), so the detail tabs and their states can be
  seen and tested anywhere. The demo never reads the real system: its GPU uses an
  empty filesystem root (a test guards this).
- **10:** scanning /proc runs only while Apps or Processes is on screen
  (pages `acquire()`/`release()` the `ProcessMonitor`); a full scan of ~330
  processes takes about 20 ms here.
- **Refactor (before M12):** dependency injection by hand.
  - `core/system.py` (`System`) holds every OS call.
  - `context.py` (`build_context` → `AppContext`) is the only place
    services are created.
  - `PageFactory` replaced the `if`-chain.
  - GPU backends receive `GpuDeps`, and `probe(gpu, deps)` replaced
    `probe(gpu, sysroot, which)`.
  - `MainWindow(app, ctx)`, and `Application(context_factory=...)`.
  - `tests/test_static.py` enforces it.
  - DESIGN.md's diagrams were brought back in line with the code (§4.2, §5,
    §7, §8, §9). The planned `ProcessSource`/`HelperSource` split became
    `ProcessMonitor.use_elevated_io()`.
- **12:**
  - The helper refuses PID 1 and its own PID.
  - The polkit policy has one action per subcommand (`exec.argv1`), plus
    `auth_admin` without caching for `intel_gpu_top`, which can write files.
  - From a source checkout, pkexec runs the helper through Python and shows
    its generic prompt.
- **12/13:** the dialogs need libadwaita 1.5 (`Adw.Dialog`), which raises
  the minimum from 1.4. Ubuntu 24.04 ships 1.5.
- **15.1:** our own app icon and Processor and Memory symbolic icons
  replace the stand-ins. `desktop-file-validate` and `appstreamcli` (pedantic)
  pass.
- **15.2:** the `.deb` builds and its contents are checked by tests.
  Installing it in a clean container wasn't possible here.
- **15.4:** measured with `tests/ui/perf.py` (1 s refresh, headless):
  - Processor page: 2.4–3 % of one CPU
  - GPU page: 2.5–2.8 %
  - Processes page: 5–6 %
  - Sampling alone, nothing drawn: about 1 % (2.9 % with the process scan)

  The rest is GTK rendering under Broadway's software renderer. On a real
  desktop it should be lower, but that wasn't measured, so the 2 % target
  is **not confirmed**. Two hot spots were fixed: `SysRoot` built a pathlib
  `Path` per read, and the `fdinfo` fd scan ran twice as often as needed.
- **15.5:** graphs and sidebar rows have accessible labels and
  descriptions. An Orca walkthrough wasn't possible here.
- **Refactor: GPU tabs (after M15).** Swapping the whole GPU page between
  backends lost the overview whenever the detail tool stopped, and hid the
  vendor view behind a menu. Now (DESIGN §7):
  - Backends have a role. The SUMMARY source (sysfs/fdinfo) always runs;
    the DETAIL source (intel_gpu_top) is optional, with its own lifecycle
    (`DetailState`: unavailable, off, needs-auth, starting, running,
    failed).
  - One `GpuPage` per GPU, never replaced: an Overview tab plus the detail
    class's `TABS` (Details, Processes), switched from the header (a bottom
    bar below 550sp). Until the source runs, each tab shows a status page
    with Show Detailed Statistics / Try Again / Turn On.
  - `DetailBackend.create_views()` returns `DetailViews` (views plus the
    backend connections feeding them), so the page disconnects stale views
    when the source restarts.
  - Settings: `gpu-backend` became `gpu-details-disabled`, plus `gpu-view`
    and `intel-gpu-top-history`. Preferences has a per-GPU switch.
  - `build_context(gpu_registry=...)` makes the backends injectable.
  - `tests/run-headless.sh` now checks the Broadway daemon really started
    (a stale daemon holding the port made every UI test fail) and removes
    its socket when interrupted.
  - `Settings` rejects a string for an array key (it was stored as a list
    of characters), found by the property tests.
- **11:** this system's cgroups differ from the forms assumed in DESIGN §8.
  GNOME 49 puts apps in `app-<id>.slice`. Snaps use
  `snap.<name>.<app>-<uuid>.scope`. All forms are handled (see
  `processes/apps.py`). `GioUnix.DesktopAppInfo` is used where available.

day of minutes and hours; a commit (10 s of rows) 0.3 ms; rolling up an

Steady state about 37 MiB, plus about 4 MiB of hours a year. That's in
line with Idea 2's figures for the larger hybrid laptop (61 readings).

**Deviations from Idea 2, and why:**

- **Times are always milliseconds**, not seconds with milliseconds only at
  fast refresh speeds: one rule, and SQLite's variable-length integers
  make the difference about a byte per row.
- **No timers of its own:** commits and housekeeping run when a reading
  arrives and their time has come. Readings arrive every refresh anyway,
  and tests need no main loop.
- **An export never overwrites** because it always writes a new folder
  (`… (2)` if the name is taken), so there's nothing to ask.
- **The old files are imported as detail** whatever their age; the first
  housekeeping summarises and expires them like any other rows.
- **Not done yet:** longer *Graph Time Range* choices (an hour, a day)
  drawn from the database and the Intel *Details* tab's own history (both
  done in Milestone 64), and Idea 1's slower commits (Idea 1 isn't built).

### Idea 1: Lightweight mode (minimal memory)

*Done as Milestone 66 (what changed from this plan is listed there).*

*Was Milestone 56. Steps are numbered L.1–L.11 so they don't clash with
milestones; when it's picked up, it becomes the next milestone.*

**Goal:** a mode that keeps Proccoli's memory as low as it can while still
showing the basic figures: processor, memory, GPU, drive, network and
battery usage, and the process list. It uses the system style and palette,
minimal graphs, no app or process icons, and leaves out anything else not
needed for those figures.

**Where the memory goes now** (measured on this machine, Ubuntu 24.04,
headless display; private memory, `RssAnon`):

| Stage | RssAnon | Python heap |
|---|---|---|
| GTK + libadwaita initialised, empty window | 15–17 MB | – |
| Proccoli's modules imported | 23 MB | 4 MB |
| Context built (pci.ids parsed: 3.6 MB of Python objects) | 40 MB | 8 MB |
| Window built (every page, all built at start) | 53 MB | 10 MB |
| Shown and running for 8 s | ~100 MB | 12 MB |

### Idea 2: Metrics history in a SQLite database (replaces the statistics files)

*Done as Milestone 62* (its deviations are listed there).

**Goal:** keep a history of every reading Proccoli shows, cheaply and for
as long as Proccoli runs (years without a restart included), without it
growing without bound; let graphs show that history at once; and let the
user export the running session's readings to files of their own.

**Decision: a SQLite database instead of files.** When this idea is
built, the statistics files of Milestone 58 (CSV per device) go away:
Proccoli no longer writes metrics to files on its own. The only metric
files are the ones the user asks for (export, below). Python's built-in
`sqlite3` is used, so nothing new to install (Ubuntu 24.04: SQLite
3.45). Measured on this machine (Ubuntu 24.04, the hybrid laptop: 61
readings per refresh across CPU with 24 threads, memory, two GPUs, a drive,
two network interfaces and a battery), one simulated hour at 1 s:

| Storage | Bytes per second | Per day | Per year, if all kept |
|---|---|---|---|
| CSV files (M58, measured from a real run) | 452 | 37 MiB | 13 GiB |
| SQLite, one row per reading (`series, time, value`) | 916 | 76 MiB | 27 GiB |
| SQLite, one table per device, readings as real numbers | 356 | 29 MiB | 10 GiB |
| **SQLite, one table per device, readings as scaled integers** | **239** | **20 MiB** | **7 GiB** |

- **Disk:** the chosen layout (last row) takes about half of what the CSV
  files take, and, unlike files, it can summarise old data in place.
- **Memory:** about the same. `sqlite3` with a 512 KiB page cache adds
  about 0.9 MiB of private memory (its library, 1.5 MiB more, is shared
  with other programs); the `csv` module alone added about 1 MiB.
- **Reading back:** the last 10 minutes of three devices took 6 ms, by an
  indexed time range, instead of parsing file tails.
- **Writing:** one transaction every 10 s in WAL mode: about as many bytes
  written to disk a day as the CSV files.

So SQLite is the lighter option overall, and much the lighter for anything
that reads the history back.

**Keeping years of history realistic.** Even the compact layout would
reach 7 GiB a year at full detail, far above the 1 GB limit, so full
detail isn't kept. Older readings are rolled up into summaries, as RRDtool,
Prometheus and netdata do:

| Level | What | Kept for | Typical size (this machine, 1 s) | Worst case |
|---|---|---|---|---|
| Detail | every reading, every refresh | 24 hours | 19.7 MiB | 185 MiB |
| Minutes | per minute: average, minimum, maximum of each reading | 30 days | 25 MiB (0.83 MiB a day) | 59 MiB |
| Hours | per hour: average, minimum, maximum | until the size cap | 7.5 MiB a year (21 KiB a day) | 18 MiB a year |

- **A day** writes about 20.6 MiB (detail, plus 0.83 MiB of minutes and
  21 KiB of hours). Kept as it is, a year would be 7 GiB: too much, hence
  the levels.
- **Steady state, typical:** 19.7 + 25 = 45 MiB plus 7.5 MiB per year:
  **about 52 MiB after a year, 120 MiB after ten.**
- **Upper bound.** Halving the yearly figure (as suggested) gives a lower
  number, not an upper bound, so the bound is a worst case instead: a
  machine with 64 logical CPUs and more devices (about 110 readings, ×1.8),
  busy (values that compress worse, ×1.3), at the fastest refresh (0.25 s,
  ×4, which affects only the detail level): **about 260 MiB after a year,
  420 MiB after ten.**
- **Size cap:** `history-max-size` (MiB, default **512**, up to 4096). Even
  the worst case stays under it for ten years, so the cap is a safety net:
  if the database ever exceeds it, the oldest hours go first, then the
  oldest minutes; detail is never cut below 1 hour. I'd keep 1 GB as the
  most it may ever take (512 MiB default, with room to raise it): 1 GB
  is a lot for a system monitor's history, and typical use stays near
  50–120 MiB.

**Design (DESIGN.md §13.2):**

- **Where:** `$XDG_STATE_HOME/proccoli/history.sqlite3` (state, like the
  log), 0600, in the 0700 folder. WAL mode, `auto_vacuum=INCREMENTAL`,
  a 512 KiB page cache.
- **Layout:** one table per device (`device` table maps device IDs to
  table names, names and kinds), `time` (UTC, integer seconds; milliseconds
  where the refresh is faster than 1 s) as the primary key, one integer
  column per reading in fixed-point units (hundredths of a percent and of
  a degree, milliwatts, kHz, bytes). A new reading (a GPU's details
  starting, CPU threads appearing) is an `ALTER TABLE … ADD COLUMN`, which
  SQLite does without rewriting. Summary tables mirror each device table
  with `<reading>_avg/_min/_max` and a sample count. A `session` table
  records each run's start and end (UTC).
- **Writing:** `HistoryStore` follows the monitors' `updated` signal like
  `StatsLog` does now, buffers rows and commits every 10 s on the main
  loop (a few milliseconds); on quit it commits what's left and records
  the session's end.
- **Housekeeping** every 10 minutes, so it works without ever quitting:
  roll finished minutes up from detail and finished hours up from minutes
  (`INSERT … SELECT avg/min/max … GROUP BY`), delete what's past its level,
  `PRAGMA incremental_vacuum` to give the space back, and enforce the cap.
  Times are UTC epochs, so time zone and daylight-saving changes don't
  matter; a clock set backwards only overwrites its own seconds
  (`INSERT OR REPLACE`).
- **Graphs from history** (what this idea was before): widening *Graph
  Time Range*, or starting Proccoli, fills each graph from the database at
  once: detail rows for the range (minute averages beyond 24 hours),
  converted from UTC to the monitor's clock, resampled to the refresh
  speed, with gaps where Proccoli wasn't running. On idle, one device at a
  time, so the window never stalls. Longer ranges (an hour, a day) can
  then be offered without keeping them in memory, which suits Idea 1.
- **Export of the running session** (required): main menu → *Export
  Statistics…* (and Preferences → *History*): the user picks a folder
  (`Gtk.FileDialog`, so it works through the desktop portal), and Proccoli
  writes, for **this session** (since Proccoli started):
  - one CSV file per device (RFC 4180, UTF-8; `time_utc` in ISO 8601 UTC
    with milliseconds, then `<reading>_<unit>` columns, values in their
    real units: the M58 format, now made only on request);
  - if the session is longer than the detail level (more than 24 hours),
    the older part from the minute level, in `<device>-minutes.csv` with
    `_avg`/`_min`/`_max` columns;
  - `export.json`: Proccoli's version, the session's start and end (UTC),
    each file's device name, kind and columns with units.

  It runs off the main loop (reads in chunks on idle, or a worker thread
  with its own connection), reports progress in a toast, and never
  overwrites files without asking. A range other than "this session"
  (the last hour, day, week) is an easy extension of the same query.
- **Settings:** `history` (on), `history-max-size` (MiB, 512), and
  `history-detail-hours` (24; 1–168). `stats-log` and
  `stats-log-max-size` are removed.
- **From the M58 files:** on the first start with the database, any
  existing `stats/*.csv` are imported (they become detail or minute rows
  by age) and the folder is removed, logged once.
- **Never** in `--demo` (made-up data), and nothing kept with `history`
  off (turning it off offers to delete the database).
- **Lightweight mode (Idea 1):** keeps the database (it costs about 1 MiB)
  but writes every 60 s instead of 10 s.

### Idea 4: One chart family everywhere

*Done as Milestone 63* (its deviations are listed there).

**Goal:** every chart in Proccoli is built, configured and laid out the
same way, so a change to how charts look or behave is made once. M60
made the Intel *Details* tab draw with the shared `Graph`, `Legend` and
`LegendChart`. This idea does the same for what sits around the graph:
how settings reach it, the card it's in, how cards are laid out, number
formats and colors.

**Why: what's still done more than one way** (taken stock during M61):

| Concern | Today | Problem |
|---|---|---|
| Settings reach graphs | Five ways: `DevicePage.add_graph` + `_set_axes` / `_set_grid` (live); Overview cards and the sidebar meters (axes and span, live, their own handlers); the NVIDIA Details tab (read **once** when it's built); the Intel Details tab (re-read at every sample, M60) | NVIDIA charts ignore *Show Graph Axes*, *Graph Time Range* and *Show Graph Grids* changes until the tab is rebuilt, and never show grids. Every new view must remember all three keys |
| Layout | Three fitting systems: `DevicePage` (`layout.fit_heights`), the Overview (`layout.plan_grid`), the Intel tab (`gpu/intel_gpu_top/grid.py`: `GraphGrid`, its own `split_columns`, `extra_heights`, `graph_cap`); the NVIDIA tab has none (a plain scrolling column of 120 px graphs) | The NVIDIA tab doesn't fill the window or use columns; the Intel grid lives in a vendor package although nothing in it is Intel's |
| The card | `GraphBox` / `DoubleGraphBox` / `LegendChart` rows in an `Adw.PreferencesGroup`; the Intel `GroupChart` (a `card` box around a `LegendChart` row, M60); `OverviewCard` (its own box) | Three ways to put a title, an info line and a graph in a card, with slightly different spacing |
| Number formats | `core.units` (pages, and the hover box since M61); `gpu/intel_gpu_top/labels.py` (`format_value`, `format_axis`); the NVIDIA view's `_format` | Intel bandwidth is always MiB/s and GiB/s, whatever *Data Units* says; Intel and NVIDIA clocks are formatted differently; the Intel temperatures (if any) don't follow *Temperature Unit* |

| Colors | `colors`, `entry_index`, `entry_base` + `color_offset`, `distinct`: four ways to pick a graph's colors | The GPU *Details* tabs don't get `entry_base`, so their first color isn't the GPU entry's color, unlike the GPU *Overview* tab beside them |
| Legend | `LegendChart` for some single-line graphs (Intel RC6, Interrupts), `GraphBox` for others (NVIDIA Temperature, Power) | A one-line chart has a legend on one tab and none on the other |

**Design (DESIGN.md §13.4):**

- **`ChartSettings`** (`ui/chart_settings.py`): the one place graphs get
  *Show Graph Axes*, *Show Graph Grids*, *Graph Time Range* and the unit
  preferences. `bind(graph, kind)` applies them now and on every change;
  `kind` (`PAGE`, `CARD`, `METER`) says which apply (meters have no grid).
  It owns its settings handlers and `release()`s them, so a view without
  its own teardown (the detail tabs) gets one through `DetailViews`. It
  also sets the hover formatter (61.3's `format_reading` with the
  preferences). `DevicePage`, `OverviewPage`, the sidebar and both detail
  tabs use it; their own handlers go.
- **`ChartGrid`** (`ui/widgets/chart_grid.py`): `GraphGrid` moved out of
  `gpu/intel_gpu_top/` (its arithmetic into `ui/layout.py`, beside
  `fit_heights`, sharing `GraphLimits`). The NVIDIA tab lays its charts
  out with it, so it fills the window in columns like the Intel tab.
- **`ChartCard`** (`ui/widgets/chart_card.py`): a card with a title, an
  info line and either one graph or a `LegendChart` body, with a
  `compact` mode. `GroupChart` becomes a `ChartCard`; the detail tabs
  build only `ChartCard`s. (`GraphBox` rows in preference groups stay for
  device pages, which look like Resources'; `ChartCard` uses the same
  `GraphPane`, so spacing matches.)
- **One rule for legends:** a chart with two or more lines gets a
  `LegendChart`; a one-line chart gets none, its value in the info line.
- **Formats through `core.units`:** detail sources record readings in
  base units (bytes per second, hertz, watts, degrees Celsius) at the
  history boundary (the Intel `History.add`, the NVIDIA sample), so
  `format_reading` and *Data Units* / *Temperature Unit* apply
  everywhere. `format_reading` gains a short form for axis labels
  (`"2 GB/s"`, `"1.5 GHz"`); `labels.format_value` / `format_axis` and

- **Value axes for every graph with a unit**, from that short form, in a

  NVIDIA clocks, power and temperature. *Show Graph Axes* turns them all
  off together.
- **Colors:** `DetailServices` gains the GPU entry's color index, so the
  detail tabs start at the GPU entry's color; `distinct` and
  `entry_base` stay the only ways a multi-line chart picks colors.
- **Enforced:** `test_static` checks that only `ui/chart_settings.py`
  reads `show-graph-axes`, `show-graph-grids` and `graph-time-range` for
  graphs, and that `Graph(` is constructed only inside `ui/widgets/`.

### Idea 5: Switch To any running app

*Done as Milestone 67.*

**Goal:** the Apps page's right-click menu offers *Switch To* for every
running app with a window, not only the ones M32 can reach, and it brings
that app's window to the front.

**What's possible** (checked on this machine, Ubuntu with GNOME Shell
50.1 on Wayland, during M61):

| Way | Works for | Status here |
|---|---|---|
| Ask the app over D-Bus, `org.freedesktop.Application.Activate` (M32) | D-Bus-activatable apps; also any running GApplication that owns its app ID on the session bus, even if its `.desktop` file doesn't say `DBusActivatable` | Works, but the call sends no **activation token**, so GNOME's focus-stealing prevention may show "… is ready" instead of raising the window. Of the apps running now only GNOME Terminal owns its name; a terminal's *activate* may open a new window rather than raise one (not tried, to leave the desktop alone) |
| Relaunch the `.desktop` entry (M32) | Apps with `SingleMainWindow=true` | Works; also needs the activation token (`GAppLaunchContext`), which M32 doesn't pass (it launches with `None`) |
| GNOME Shell's own D-Bus `org.gnome.Shell.FocusApp(app_id)` | Every app | **Refused:** "FocusApp is not allowed". GNOME 41+ allows it only to a short list of GNOME's own programs; `Eval` is refused too |
| `wmctrl` / `_NET_ACTIVE_WINDOW` (X11), matched by `_NET_WM_PID` | Every window in an X11 session; under Wayland only X11 apps running through XWayland | `wmctrl` isn't installed; Ubuntu's default session is Wayland |
| A **GNOME Shell extension** that exposes windows over D-Bus (list windows with their PIDs and app IDs, activate one) | Every window on GNOME, X11 or Wayland: the extension runs inside the Shell, which may focus any window | Not installed. Existing ones ("Window Calls" and similar) do this; Proccoli could also ship a small one of its own |
| KDE: KWin scripting over D-Bus | Every window on KDE Plasma | Not this desktop; possible later behind the same interface |

So **there's no way for an ordinary app to focus another app's window on
GNOME Wayland**; that's deliberate on GNOME's side. The only way to do it
for every app is code running inside the Shell, i.e. an extension the
user installs and enables once (and, on Wayland, logs out and in again
the first time).

**Design (DESIGN.md §13.5):**

- **`WindowSwitcher`** (`core/windows.py`, through `System`, faked in
  tests): `can_switch(app)` and `switch(app)`, trying in order:
  1. **Proccoli's Shell extension** if it's enabled
     (`proccoli-windows@mamadingleberry.github.io`, about 60 lines of
     GJS, shipped in the `.deb` under
     `/usr/share/gnome-shell/extensions/`): a D-Bus object
     `io.github.mamadingleberry.Proccoli.Windows` with `List() →
     [(window id, pid, app id, title)]` and `Activate(window id)`.
     Proccoli matches an app's PIDs (`App.pids`) to window PIDs, so it
     works for Firefox, VS Code, terminals and anything else with a
     window. Its only powers are listing and activating windows, and
     only on the user's own session bus.
  2. **D-Bus activation with an activation token** (M32, fixed): the
     token from `Gdk.Display.get_app_launch_context()` goes in
     `platform-data` (`activation-token`, `desktop-startup-id`), and
     relaunches pass the same launch context. Also for running
     GApplications that own their app ID on the bus.
  3. **X11:** `_NET_ACTIVE_WINDOW` for the app's windows when the session
     is X11 (or the app runs through XWayland), if `wmctrl` is
     installed. (An optional dependency, like `dmidecode`.)
- **The menu:** *Switch To* shows for every app with a window when the
  extension is on. Without it, for apps the other ways reach. Apps it
  can't reach get a greyed *Switch To* whose hover text says how to turn
  on the extension (once per session, a toast offers *Enable…*, which
  runs `gnome-extensions enable` and explains the log-out on Wayland).
- **Preferences → General:** *Window Switching*: whether the extension
  is installed and enabled, with a button to enable it.

### Idea 6: Update Interval instead of Refresh Speed

*Done as Milestone 65.*

**Goal:** a plainer, safer choice of how often Proccoli takes readings.
*Refresh Speed* (from Resources) offers five vague words, and its fastest
settings, 0.5 s and 0.25 s, go too fast: every device, the process scan,
every graph and the history database run up to four times a second. That
costs processor time and battery for changes nobody can read that
quickly, and it makes the history and the *Details* tabs store four times
the rows.

**Why: what's wrong today**

| Today | Problem |
|---|---|
| *Very Slow, Slow, Normal, Fast, Very Fast* | The words don't say how often; users can't tell 0.5 s from 0.25 s |
| 0.25 s and 0.5 s | Too fast: a full refresh of every device and every process 4 times a second; the history writes 4× the rows; the Intel tab's *Update Interval* menu offers 0.25 s too |
| Slowest is 4 s | No choice for a quiet machine or a battery (5 or 10 s) |

**Design:**

- `update-interval` (enum, nicks `1-second`, `2-seconds`, `3-seconds`,
  `5-seconds`, `10-seconds`; **default 1 second**, what *Normal* was).
  Preferences → General → *Update Interval* with the times spelled out.
  Nothing faster than 1 s.
- `refresh-speed` stays in the schema only to **migrate** a choice once
  at start-up: *Very Slow* (4 s) → 5 seconds, *Slow* (2 s) → 2 seconds,
  anything else → 1 second; then it's reset, so the migration runs once
  and never again.
- The Intel tab's own interval (`intel-gpu-top-interval`) takes the same
  nicks (empty: the *Update Interval*); its old refresh-speed nicks are
  mapped the same way when read, and migrated at start-up.
- `core.ticker`: `UPDATE_INTERVALS_MS`, `interval_for(nick)` (new and old
  nicks), `update_interval_ms(settings)`; every reader of
  `refresh-speed` (ticker, device manager, history, charts, Processes,
  Intel and NVIDIA backends) reads `update-interval` instead.

| Step | Create / change | Test |
|---|---|---|
| I6.1 | Schema `update-interval` (enum); `core.ticker` intervals and `update_interval_ms`; every reader switched | Unit: intervals; the ticker follows the new key; the manager resizes on it |
| I6.2 | `core/settings.py`: `migrate(settings)` (refresh-speed and old Intel nicks, once); called by `Application` after loading | Unit: each old value, run twice, nothing to do on a fresh install |
| I6.3 | Preferences *Update Interval*; the Intel *Update Interval* menu and preference with the new choices | Dialog test; UI: the Intel menu |
| I6.4 | README, DESIGN §11 | – |

**Done when:** no choice refreshes faster than once a second, a user's
old choice carries over once, and nothing reads `refresh-speed` except
the migration.

### Idea 7: Export Statistics for the session or the whole saved history

**Goal:** *Export Statistics…* lets the user choose what to export: **this
session** (since Proccoli started, what it does now) or **the saved
history** (everything in the database, across every run), plus a few
ranges in between.

**Why:** today the export always covers the running session only
(Milestone 62). The database usually holds much more: a day of every
reading, a month of minute summaries, and hours going back as far as the
size cap allows. To get at the rest, a user has to query
`history.sqlite3` with their own tools.

**Design (DESIGN.md §13.6):**

- **A choice before the folder picker:** an `Adw.Dialog` *Export
  Statistics* with a *What to Export* combo:
  - *This Session* (the default, today's behaviour);
  - *Last Hour*, *Last Day*, *Last Week*;
  - *All Saved History*.

  Under it, what that covers and an estimate ("about 3 days, 2 sessions,
  about 40 MB of CSV"), then *Export…*, which opens the folder picker as
  now.
- **One export function for any range:** `export_session` becomes
  `export_range(db_path, parent, start_ms, end_ms, scope)`. Each level
  goes in its own file per device, and only for the part of the range
  that level holds, so no time appears twice:
  - `<device>.csv`: every reading, where detail is kept;
  - `<device>-minutes.csv`: minute average, minimum and maximum, where
    only minutes are kept;
  - `<device>-hours.csv`: the same per hour, older than that.
- **`export.json`** gains the scope, the range (UTC), every session in it
  (start and end, so gaps where Proccoli wasn't running can be told from
  missing data), and each file's level and time span.

### Idea 8: Lightweight Mode: small charts on the Overview, a minimal sidebar

**Goal:** in Lightweight Mode the Overview shows each device's trend
again, as the small line chart the sidebar uses, and it keeps the
busiest apps and processes. The sidebar can only be *Icons Only* or
*Hidden*, never *Full*.

**Why:** Milestone 66 made the lightweight Overview a plain list of
readings, with no charts and without the busiest apps and processes, and
kept the full sidebar (with progress bars).
So at a glance there's no trend anywhere, while the sidebar's full
entries still repeat the Overview's figures. Moving the small charts to
the Overview and keeping the sidebar to icons puts the trend where people
look, and the window draws about the same number of charts as before:
one small chart per device, in one place instead of two. With the sidebar
down to icons (or hidden), the Overview is the one page that shows what's
going on, so what's using the machine belongs there too.

**Design (DESIGN.md §13.7):**

- **Overview cards in Lightweight Mode:** name, readings, and under them
  the sidebar's small chart (`Graph(GraphStyle.SMALL)`, 36 px high, in
  the entry's color, network's receive and send on one automatic
  scale). It's the same as `Meter`'s graph, so it has no hover and no
  axes; axes stay pinned off. Its time range is the pinned one (at most
  1 minute), so it costs what a sidebar meter did. `OverviewCard(chart=
  "small")` (`"full"` / `"small"` / none instead of `True`/`False`); the
  page keeps its 3-column list layout (no grid fitting) and binds the
  graphs as `ChartKind.METER`.
- **The busiest apps and processes stay on the Overview** in Lightweight
  Mode: the two `TopTable`s below the cards (5 each, ranked by
  `overview-top-by`), as in the full mode, but **without icons**
  (`profile.app_icons` is off, so `TopTable.fill` leaves the icon out and
  the image isn't built). `Profile.overview_tables` becomes true for
  Lightweight Mode. The process scan still runs only while the Overview,
  Apps or Processes is on screen (`ProcessMonitor.acquire`/`release`), and
  with nobody showing it the process list is still dropped
  (`keep_process_data`, M66). So the tables cost only while they're
  visible. A click on a row opens Apps or Processes (built on visit) as
  now.
- **The sidebar:** `sidebar-style` is pinned to *Icons Only*
  (`ProfileSettings`), so it stays *Icons Only* or *Hidden*
  (`sidebar-shown`). The main menu's *Sidebar* section lists only *Icons
  Only* and *Hidden* (`primary_menu(modes=…)`), and `SidebarVisibility`
  turns a request for *Full* (a stale action target, F9 toggling back)
  into *Icons Only*. The pin on `sidebar-meter-type` (progress bars) is
  no longer needed: an icons-only sidebar shows no meters at all, so
  their widgets aren't built (`StackSidebarItem` builds its meter on
  first use).
- **Memory, measured not assumed** (`tests/ui/mem.py`): the sidebar's
  meters go; the Overview's small charts and its two tables (and the
  process scan while it's shown) come in. Charts alone should be no worse
  than Milestone 66 (37.8 MiB at start). The tables add the process list
  while the Overview is open, a few MiB; the plan records both numbers
  rather than assuming either, and the README's "about half the memory"
  is corrected if they don't support it.

### Idea 9: Custom graph time range

**Goal:** besides the presets (30 seconds to 1 day), the user can type
any range: a number and a unit (seconds, minutes, hours or days), from
**10 seconds to 30 days**.

**Why:** the presets jump from 1 hour to 6 hours to 1 day. A range like
"the last 3 hours" (since lunch) or "the last 2 days" (since the weekend)
isn't on the list.

**What it costs in memory: nothing extra.** A graph never holds more
than `MAX_GRAPH_POINTS` (1200) points. A longer range doesn't keep more
points: each point averages more readings (`history_plan`: a day at 1 s
is 1184 points of 73 readings; 30 days would be 1200 points of 2160).
The averager keeps running sums, not the readings. So a series costs
about 40 KB at any range (1200 floats and their times in deques), and a
whole window a few MiB at most, the same as the 1-day preset today.
What a long range does cost:

- **Where the data comes from.** Graphs are filled from the history
  database (M62), and it keeps detail for `history-detail-hours` (24 h by
  default), minute averages for 30 days, and hour averages until the
  size cap. **30 days is the limit because that's how long minutes are
  kept.** At 30 days a point is 36 minutes, so minute averages are
  enough; hour averages would leave gaps between points. Going further
  is what *Export Statistics* (Idea 7) is for.
- **Without the history** (*Keep History* off, or `--demo`) a graph only
  fills while Proccoli runs. A long range then is mostly empty on the
  left; the Preferences row says so.
- **Filling a long graph** reads at most 1200 buckets per device from
  the minutes table in one grouped query (`HistoryDb.buckets`), a few
  milliseconds, on the idle queue one device at a time as now.
- **Resolution, not memory.** At 30 days, a spike shorter than a point
  (36 min) is averaged away. The hover's heading says how long a point
  is ("each point: 36 min").

**Design (DESIGN.md §13.8):**

- **Settings:** `graph-time-range` gains a `custom` nick, and a new key
  `graph-time-range-custom` (`u`, seconds, default 7200) holds the value.
  `time_range_s(settings)` returns the custom seconds, clamped to
  `MIN_RANGE_S` (10 s, and at least 2 update intervals) and `MAX_RANGE_S`
  (30 days), when the nick is `custom`. All callers (`graph_plan`, the
  Intel backend, `ChartSettings`) go through it, so nothing else needs to
  know about custom ranges.
- **Preferences:** the *Graph Time Range* combo gets *Custom…*. Picking
  it shows a row below it with a `Gtk.SpinButton` (the number) and a
  `Gtk.DropDown` (seconds / minutes / hours / days). The value is
  clamped as you type, and the subtitle names the limit when you hit it.
  A custom range that matches a preset is still stored as custom (it's
  what the user typed).
- **Axes:** `span_unit` / `format_span` gain days ("2 d") above
  48 hours, and `NICE_STEPS` gets 2 d and 7 d, so the ticks
  stay round for any range.
- **Lightweight Mode** pins the range to at most 1 minute
  (`_at_most_one_minute`); it must treat `custom` by its seconds.
- **Depends on Bug 1** (below): changing the range has to refill the
  graphs, or each change shows the same stretching.

### Idea 10: Shade the time Proccoli wasn't running

*Done as Milestone 68* (its decisions are listed there).

**Goal:** where a graph has no data because Proccoli was closed, it
shows a **dithered dark vertical bar** over that stretch, so a gap reads
as "not recording" and not as zero or a lost line.

**Why:** with the history database (M62), a long graph spans earlier
runs. Today the time between them is just a break in the line, which
looks the same as a sensor with no reading, and on an area chart it's
easy to miss. The user can't tell "the machine was idle" from "nothing
was watching".

**Which gaps get the bar:** only time **outside every recorded session**
(`HistoryDb.sessions()`: each run's start and end; the end moves forward
with every commit, so a crash loses at most `COMMIT_EVERY_S`). A `None`
inside a session (a reading a device didn't give, a monitor failing for
a while, `add_gap`) stays a plain break in the line, as now. Time before
the first session ever recorded counts as not recording too.

**Design (DESIGN.md §13.9):**

- **The data:** `History` gets an `offline` deque beside `times` (a bool
  per point, same `maxlen`). `HistoryStore._fill` marks each backfilled
  slot whose time span lies outside every session (one read of the
  session table, merged with the slots in one pass); live points are
  never offline. `History.offline_runs()` gives the runs as
  `(first index, last index)`, so the graph doesn't scan per frame. The
  regrouping of Bug 1 carries the flags along (a slot is offline only if
  all its points were).
- **Without the history** (*Keep History* off, `--demo`) nothing is ever
  offline: the graph only holds this run.
- **Drawing (`ui/widgets/graph.py`):** after the grid and before the
  lines, each offline run is filled with a **2×2 device-pixel checker
  pattern** (`cairo.SurfacePattern` from a small `ImageSurface`,
  `EXTEND_REPEAT`, built once per scale factor), black at about 35 %
  alpha, clipped to the plot area. Pixel-aligned with `snap_to_device`
  so the dither stays crisp at fractional scales. Its x range uses the
  same index-to-x mapping as `graph_runs`, so bars and lines line up.
- **Hover:** over a bar the hover heading says "Proccoli not running"
  with the span ("2 h 10 min"), instead of empty readings.
- **Small graphs** (sidebar meters, `GraphStyle.SMALL`) skip the bars:
  they show at most a minute, always this run.
- Same for the GPU Details charts (`chart_grid.py`), which draw through
  the same `Graph`.

## Bugs

Found but not fixed. Each is fixed as its own change, with a regression
test. DESIGN.md §14 has the cause and the fix design of each.

### Bug 1: Graphs stretch old points after a time range change

*Fixed in Milestone 68.* As built: a shorter step empties the history
instead of regrouping it (what lay between the old points is gone), and
the store refills it from the database.

**Seen:** on 0.3.0, about 3 hours after first running it, the graphs on
*1 Day* were full from edge to edge, as if they held 24 hours of data.
The history database held 3.2 hours (15:03 to 18:15).

**Cause:** a graph has no time per point. `graph_runs` draws its points
evenly by index, newest at the right, and treats them as `step_s` apart.
`step_s` depends on the range (at 1 s updates: 1 minute 1 s, 1 hour
4 s, 6 hours 19 s, 1 day 73 s). When the range changes,
`History.set_plan()` keeps the points it holds, at their old spacing,
and the history store's `backfill_all()` only fills the room *in front
of* them. The log showed it exactly when the range went from 1 minute to
1 hour to 6 hours to 1 day: 840 points backfilled (901 − 61), then 236
(1137 − 901), then 47 (1184 − 1137). The 1-day graph then held about a
minute of 1 s points, an hour of 4 s points and 75 minutes of 19 s
points, drawn 73 s apart. The time axis and the hover's "… ago" are
wrong for everything but the newest minute. The Intel GPU Details history
(`gpu/intel_gpu_top/history.py`) has the same flaw.

The database side is right: backfilling an empty graph on *1 Day* from
the same database fills only the right-hand 3.2 hours (159 points).

**Fix:**

- When `set_plan` changes `step_s` (or `every`), the history is
  **regrouped**: its points are put into the new step's slots by their
  own times (averaging where several fall into one slot, gaps where none
  does), so it's right even without the database.
- Then, with *Keep History* on, `backfill_all()` refills it **in full**
  from the database instead of just the room in front: clear, then
  `_fill` with the whole plan. The database has every reading at full
  detail for `history-detail-hours`, so nothing is lost, and the newest
  half-made point carries over.
- The same for the Details histories (`detail_history()`).
